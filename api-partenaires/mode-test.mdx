## Mode test (bac à sable)

Avec une clé `wk_test_`, vous travaillez dans **votre bac à sable** : un
marchand fictif (« Boutique de test Woura »), un partenariat accepté avec
lui, et des commandes fictives. Il vit sur les serveurs de production, mais
**rien n'y a d'effet réel** : aucun message au client, aucun stock réel, aucun
argent. Toutes les routes ci-dessus marchent, sur les seules données du bac à
sable ; les événements partent vers vos points `test`.

Simuler ce que ferait un marchand :

| Méthode | Chemin | Simule |
|---|---|---|
| POST | `/test/shipments` | Une commande qui vous est assignée → `shipment.assigned` |
| POST | `/test/shipments/{id}/cancel` | Le marchand annule (`{"reason"}` facultatif) → `shipment.cancelled` (au journal, `actor: system`) |
| POST | `/test/shipments/{id}/update` | Le marchand retouche (`address`, `city`, `note`, `items_amount`) → `shipment.updated` |
| POST | `/test/stock-transfers` | Le marchand vous envoie du stock (`product_name`, `quantity`, `comment`) → `stock_transfer.requested` |
| POST | `/test/partnership-requests` | Un nouveau marchand fictif vous demande (`merchant_name`, `message`) → `partnership.requested` |
| POST | `/test/statements/weekly-run` | L'émission du lundi sur votre bac à sable, jusqu'à `period_end` (aujourd'hui par défaut) → `statement.issued` pour chaque relevé émis |
| POST | `/test/statements/{id}/confirm` | Le marchand confirme le versement d'un relevé `paid` → `statement.confirmed` |
| POST | `/test/statements/{id}/dispute` | Le marchand conteste un relevé `issued` ou `paid` (`{"comment"}` facultatif) → `statement.disputed` |
| POST | `/test/orders` | Une commande à confirmer chez le marchand fictif (`items`, `customer`, `address_details`, `delivery_fee`, `delivery_fee_included`, `note`, tous facultatifs) ; l'option y est active d'office → `order.confirmation_requested` |
| POST | `/test/orders/{id}/withdraw` | Le marchand confirme (`{"reason": "confirmed_by_merchant"}`) ou annule (`cancelled_by_merchant`) lui-même → `order.confirmation_withdrawn` |
| POST | `/test/order-confirmation-requests` | Un nouveau marchand fictif, déjà partenaire, allume l'option (`merchant_name`) → `order_confirmation.requested` ; répondez par `/merchants/{id}/order-confirmation/accept` ou `/refuse` |
| POST | `/test/merchants/{id}/order-confirmation/disable` | Le marchand coupe l'option → `order_confirmation.updated`, et `order.confirmation_withdrawn` pour chaque commande encore en attente |
| POST | `/test/merchants/{id}/order-confirmation/call-fee` | Le marchand répond à votre prix d'appel (`{"decision": "accept"}` ou `"refuse"`) → `order_confirmation.updated` |

`POST /test/shipments` (tout est facultatif) :

```json
{
  "mode": "pickup",
  "accept_automatically": false,
  "items": [{"name": "Robe wax", "sku": "RW-38", "quantity": 2, "unit_price": 7500}],
  "delivery_fee": 1500,
  "delivery_fee_included": true,
  "customer": {"name": "Client test", "address": "Fidjrossè, rue 12", "city": "Cotonou", "country": "BJ"},
  "note": "Appeler avant de passer"
}
```

Plafonds par société : 500 commandes de test et 200 transferts de test par
24 heures, 20 marchands fictifs en tout (`409 sandbox_limit_reached`).

Sans `delivery_fee`, le tarif de la grille de votre bac à sable pour la ville
du client ([zones et tarifs](/api-partenaires/zones) : `PUT /zones` avec votre
clé de test), sinon 1 500. Sans `items`, un article de test au prix
`cod_amount` (15 000 par défaut). Le
téléphone du client est fictif (+999…). En mode `depot`, le stock n'est pas
contrôlé dans le bac à sable. Les [relevés](/api-partenaires/releves) marchent
comme en live sur les livraisons du bac à sable (`merchant_id` : celui de la
« Boutique de test Woura », dans `GET /merchants`) ; l'émission du lundi ne
tourne qu'en live, `/test/statements/weekly-run` la simule. Seul
`statement.cancelled` émis par l'équipe Woura ne se simule pas. Les routes `/test/…` répondent
`403 test_key_required` avec une clé live, et `POST /merchant-invitations`
n'envoie rien avec une clé de test (même réponse).

## Questions ouvertes

Vos réponses peuvent encore faire évoluer cette API :

1. La liste exacte de vos statuts internes, pour vérifier la correspondance du [statuts](/api-partenaires/livraisons).
2. Stock en entrepôt chez vous (`depot`), ramassage chez le marchand (`pickup`), ou les deux ?
3. Preuve de livraison captée : photo, code, signature ?
4. Reversement COD aujourd'hui : fréquence, moyen, forme du relevé, frais retenus.
5. Votre grille : chargez-la par `PUT /zones` ([zones et tarifs](/api-partenaires/zones)), ou
   envoyez-nous le fichier (une ligne par ville ou commune : pays, ville,
   commune, tarif, délai en heures, votre code de zone).
6. Volume par jour, nombre de marchands à amener, et contact technique.
7. Confirmez-vous les commandes par téléphone pour vos e-commerçants
   ([confirmation des commandes](/api-partenaires/confirmation)) ? Si oui : avec quels résultats d'appel
   (les nôtres : confirmée, annulée, à rappeler, injoignable), et à quel prix
   par commande confirmée ?
